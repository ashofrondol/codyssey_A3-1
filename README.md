## 프로젝트 개요

**컴퓨터 비전**(컴퓨터가 이미지와 영상을 이해하고 처리하게 하는 기술)으로, 비스듬하게 찍힌 문서 사진을 자동으로 찾아 정면에서 본 것처럼 반듯하게 펴 주는 문서 스캐너를 OpenCV와 NumPy로 직접 만든다. 노이즈 제거 → **엣지 검출**(밝기가 갑자기 바뀌는 경계선 찾기) → **윤곽선 추출**(닫힌 테두리 찾기) → **투시 변환**(비스듬한 사각형을 직사각형으로 펴는 변환)으로 이어지는 처리 과정을 설계하고, 단계마다 이미지가 어떻게 바뀌는지 눈으로 확인한다. 활용 예로 차량 검사 보고서·제조 라벨(AI Mobility / Smart Factory), 처방전·검사 결과지(Healthcare), 영수증·송장(E-Commerce)을 현장에서 바로 디지털화하는 상황이 있다. 이 과정에서 "사람이 규칙을 설계하는 방식"의 한계를 직접 겪어 보고, 이후 머신러닝·딥러닝의 "데이터로부터 학습하는 방식"이 왜 필요한지 스스로 답할 수 있게 되는 것이 목표다.

**핵심 과제** (명세의 "최종 결과물")

1. 이미지 경로를 입력하면 처리 과정을 단계별 윈도우로 보여 주고, 트랙바로 파라미터를 조절할 수 있는 문서 스캐너 애플리케이션을 만든다.
2. 복잡한 배경 위의 문서를 자동으로 찾아 반듯한 직사각형으로 펴고, 적응형 이진화로 글씨를 선명하게 만든다.
3. 20장의 테스트 이미지로 성공률을 측정하고, 실패 조건과 규칙 기반 접근의 한계를 분석 보고서로 정리한다.

## 학습 목표

과제를 마치면 아래를 스스로 설명할 수 있어야 한다. (명세 "과제 목표")

- 컨볼루션 연산이 필터와 이미지의 내적임을 이해하고, 행렬 곱셈이 이미지의 기하학적 변환(회전, 투영)을 수행하는 원리
- 하나의 고정된 파라미터가 다양한 환경(조명, 각도, 배경)에서 왜 실패하는지 정량적 데이터를 근거로 설명하기

## 개발 환경과 제약 사항

**개발 환경**

- Python 3.8 이상
- 필수 라이브러리: OpenCV (`opencv-python>=4.5`), NumPy (`numpy>=1.20`)
- 시각화용 (선택): Matplotlib (`matplotlib>=3.3`), Seaborn
- 최소 사양: Python 3.8+, RAM 4GB 이상, 웹캠 사용 시 USB/내장 카메라
- 로컬 권장: 트랙바/`imshow` 등 GUI 기능은 로컬 환경(Windows/Mac/Linux 데스크톱)에서 정상 동작한다.
- Colab 대안: GUI가 불가능한 환경에서는 `imwrite`로 이미지를 저장하고, 파라미터는 명령줄 인자 또는 설정 파일로 입력받는 방식으로 대체한다.
- 웹캠 사용 시 OS별 카메라 권한 허용이 필요할 수 있다.

**금지 사항**

- PyTorch, TensorFlow, Keras 등 딥러닝 프레임워크 사용 금지
- Tesseract OCR 등 완성된 OCR 라이브러리 사용 금지
- 좌표 정렬 로직은 라이브러리에 의존하지 않고 직접 구현한다.
- 허용: Python 내장 `sorted()`, NumPy 연산(`np.argsort`, `np.sum` 등)으로 좌표 정렬
- 허용: OpenCV의 `findContours`, `approxPolyDP`, `getPerspectiveTransform` 등 기본 함수
- 금지: `scipy.spatial`, `shapely` 등 외부 기하 라이브러리로 좌표 정렬/변환 수행
- 보너스 3 한정으로 Pillow(PIL), FPDF, reportlab 등 PDF 생성 라이브러리 사용 허용

**데이터셋 조건**

- 직접 촬영한 20장의 이미지에 대해 테스트를 수행한다. (사진을 촬영할 수 없는 환경이라면 제공한 이미지로 진행)
- 표준 테스트셋: 촬영이 어려우면 LMS 과제 페이지에서 표준 테스트 이미지 20장을 내려받는다. 경로: [LMS] > 과제자료 > `cv19_test_images.zip`
- 추가 촬영 이미지는 보너스 가점으로 처리한다.
- 정량적 성능 평가 결과가 보고서에 포함되어야 한다.

### 먼저 확인할 것: 직접 촬영이 기본이다

명세는 "직접 촬영한 20장의 이미지에 대해 테스트를 수행해야 한다"고 정한다. 촬영할 수 없을 때의 대안으로는 LMS의 표준 테스트 이미지 20장만 적혀 있고, **다른 공개 데이터셋으로 20장을 대신해도 된다는 말은 없다.** 그래서 순서는 다음과 같다.

1. 본인 휴대폰으로 20장을 찍는다. 이것이 1순위다.
2. 촬영이 정말 어렵다면 LMS의 `cv19_test_images.zip`을 쓴다.
3. 아래 공개 데이터셋은 **20장을 대신하는 용도가 아니라**, 파라미터를 미리 시험하거나 추가 실험을 할 때 쓰는 보충 자료다. 공개 데이터로 20장을 채우고 싶다면 운영진에게 먼저 확인한다.

**직접 찍을 때의 촬영 계획 예시** (보고서 표의 4가지 조건 × 5장)

| 조건 | 장수 | 찍는 방법 예시 |
|---|---|---|
| 단순 배경 + 정면 | 5 | 단색 책상이나 바닥에 문서를 놓고, 위에서 똑바로 내려다보며 찍는다. 조명은 고르게 한다 |
| 그림자 있음 | 5 | 휴대폰이나 손의 그림자가 문서 위에 걸치게 찍는다. 약한 그림자와 강한 그림자를 섞는다 |
| 45도 이상 기울어짐 | 5 | 문서를 비스듬히 내려다보는 각도(사다리꼴로 보이게)로 찍는다 |
| 복잡한 배경 | 5 | 무늬가 있는 천, 책과 물건이 어지러운 책상, 문서와 밝기가 비슷한 흰 책상 위에서 찍는다 |

명세의 어려운 케이스에는 구겨짐, 부분 가림도 있다. 위 표에는 행이 없으므로, 어느 조건 행에 넣었는지 촬영 조건 기록에 함께 적는다([명세에서 확인할 점](#명세에서-확인할-점) 참고). 영수증, A4 용지, 명함을 골고루 섞으면 "문서 종류"도 함께 비교할 수 있다.

### 데이터를 다룰 때 주의할 점

- **원본 이미지는 레포에 올리지 않는다.** `data/` 폴더에 두고 `.gitignore`로 제외했다. 공개 데이터셋은 다운로드 위치와 출처, 라이선스만 README에 적는다.
- **직접 찍은 사진의 개인정보**: 영수증의 카드 번호 끝자리, 명함의 이름과 전화번호, 처방전 같은 서류에는 개인정보가 있다. 개인정보가 없는 문서(인쇄한 연습용 페이지, 이미 공개된 안내문 등)를 찍거나, 결과 이미지를 레포에 올릴 때는 해당 부분을 가린다.
- **출처 표기**: SmartDoc을 쓰면 CC BY 4.0에 따라 출처와 라이선스를 밝힌다. 대회 페이지는 ICDAR 2015 SmartDoc 대회 논문을 인용해 달라고 요청하므로, 그 페이지에 적힌 논문 정보와 데이터 주소(`https://doi.org/10.5281/zenodo.1230217`)를 함께 적는다.
- **촬영 조건 기록 형식**: 명세는 이미지마다 조명, 각도, 배경 복잡도를 기록하라고 한다. `data/images/conditions.csv`처럼 파일명, 문서 종류, 조건 행(보고서 표의 4가지 중 하나), 조명, 각도, 배경, 메모를 한 줄씩 적어 두면 성공률 표를 만들 때 바로 쓸 수 있다. 이 기록 파일은 개인정보가 없으면 레포에 올려도 된다(이때는 `.gitignore`에 예외를 추가한다).
- **사진 크기**: 요즘 휴대폰 사진은 4000픽셀이 넘어서 처리와 창 띄우기가 느리다. 처리 전에 `cv2.resize`로 줄이고, 줄인 비율만큼 꼭짓점 좌표를 다시 키워서 원본에 투시 변환을 적용하면 결과 화질을 유지할 수 있다.

## 할 일

명세의 기능 요구 사항이다. 끝낸 항목은 `[x]`로 바꾼다.

### 1. 데이터 수집

알고리즘을 시험할 문서 사진을 쉬운 경우와 어려운 경우로 나눠 모은다.

- [ ] 본인의 스마트폰으로 문서 사진 20장을 직접 촬영한다. (촬영이 어려운 환경이라면 표준 테스트셋으로 진행)
- [ ] 쉬운 케이스 5장: 단순 배경, 정면 촬영, 균일한 조명
- [ ] 어려운 케이스 15장: 그림자, 구겨짐, 복잡한 배경, 45도 이상 기울어짐, 부분 가림 등
- [ ] 각 이미지에 대해 촬영 조건(조명, 각도, 배경 복잡도)을 기록한다.

### 2. 이미지 탐색적 분석 (EDA)

픽셀 히스토그램(밝기값마다 픽셀이 몇 개인지 센 막대그래프)으로 사진의 밝기 특성을 살펴본다.

- [ ] 각 이미지의 픽셀 히스토그램을 분석하고, 밝기 분포의 특성을 파악한다.
- [ ] 쉬운 케이스와 어려운 케이스의 히스토그램 차이를 시각화한다.
- [ ] "왜 어두운 이미지에서 엣지 검출이 어려운지"를 분포 관점에서 설명한다.

### 3. 이미지 전처리 및 엣지 검출

흑백으로 바꾸고 살짝 흐리게 해서 잡티를 줄인 뒤, 문서의 테두리 선을 찾는다. 가우시안 블러는 주변 픽셀과 가중 평균을 내어 흐리게 하는 필터이고, Canny는 대표적인 엣지 검출 방법이다.

- [ ] 컬러 이미지를 Grayscale로 변환한다.
- [ ] 가우시안 블러를 적용해 노이즈를 제거한다.
- [ ] Canny Edge Detection을 사용하여 문서의 외곽선을 검출한다.
- [ ] 트랙바를 만들어 블러 강도(커널 크기)와 Canny 임계값(low, high)을 실시간으로 조절할 수 있게 한다.

### 4. 문서 윤곽선 추출

엣지 중에서 닫힌 테두리를 찾고, 그중 꼭짓점이 4개인 사각형을 문서로 고른다.

- [ ] 검출된 엣지에서 닫힌 윤곽선(contour)을 찾는다.
- [ ] 면적 필터링을 통해 작은 노이즈를 제거한다.
- [ ] `approxPolyDP`를 사용하여 꼭짓점이 4개인 사각형 도형을 찾는다.
- [ ] 검출된 사각형을 원본 이미지 위에 시각화한다.

### 5. 기하학적 변환

찾은 네 꼭짓점을 정해진 순서로 놓고, 그 사각형을 직사각형으로 펴는 변환을 적용한다.

- [ ] 찾아낸 4개의 좌표를 순서대로 정렬한다(좌상-우상-우하-좌하).
- [ ] 좌표 정렬 로직은 라이브러리에 의존하지 않고 기하학적 원리로 직접 구현한다.
- [ ] `getPerspectiveTransform`과 `warpPerspective`를 사용하여 이미지를 직사각형으로 변환한다.

### 6. 이미지 후처리

펴진 이미지를 글씨는 검정, 배경은 흰색인 스캔본으로 만든다. 적응형 이진화는 이미지 전체에 기준값 하나를 쓰지 않고 부분마다 기준값을 따로 정해 흑백으로 나누는 방법이다.

- [ ] 변환된 이미지에 적응형 이진화(Adaptive Thresholding)를 적용하여 깔끔한 스캔본을 만든다.
- [ ] 결과물을 이미지 파일(jpg/png)로 저장한다.

### 7. 정량적 성능 평가

20장 전체에서 성공과 실패를 세어 조건별 성공률로 정리한다.

- [ ] 성공 기준: 4개의 꼭짓점이 올바르게 검출되어 문서가 반듯하게 변환됨
- [ ] 조건별(조명, 각도, 배경) 성공률을 표로 정리한다.

## 결과 예시 (명세 참고)

명세는 아래가 정답이 아니라 참고 예시이며, 실제 구현은 얼마든지 달라도 된다고 밝힌다.

- **실행 화면 예시**: Original(원본) → Preprocessed(그레이스케일 + 블러) → Edges(Canny 결과) → Contours(검출된 사각형을 빨간색으로 표시) → Result(투시 변환 + 이진화된 최종 스캔본)의 5개 윈도우와, Blur Kernel(예: 7), Canny Low(예: 50), Canny High(예: 150)를 조절하는 트랙바 패널.
- **성공 케이스**: 책상 위에 45도로 놓인 A4 용지 → 정면에서 본 듯한 반듯한 A4 이미지(`scanned_001.jpg`).
- **부분 성공 케이스**: 약간의 그림자가 있는 영수증 → 4꼭짓점 검출과 변환은 성공했으나 종횡비가 원본 대비 7% 차이. 텍스트는 판독 가능.
- **실패 케이스**:

```
입력: 강한 그림자가 있는 영수증
문제: 그림자 경계가 엣지로 검출되어 문서 윤곽선이 왜곡됨
시도: Canny 임계값 상향 → 문서 엣지도 함께 사라짐
결론: 단일 파라미터로 해결 불가
```

- **보고서 요구 사항이 확정인지**: 보고서 절 제목이 "보고서 요구 사항(확인 필요)"로 되어 있어, 이 요구 사항이 최종본인지 명세상 분명하지 않다.
- **테스트 결과 표와 어려운 케이스 조건이 다름**: 데이터 수집의 어려운 케이스는 "그림자, 구겨짐, 복잡한 배경, 45도 이상 기울어짐, 부분 가림 등" 15장인데, 보고서 표는 "그림자 있음", "45도 이상 기울어짐", "복잡한 배경" 각 5장으로 3가지 조건만 있다. 구겨짐, 부분 가림 사진을 표의 어느 행에 넣을지 나와 있지 않다. 또 기능 요구 사항 7은 "조건별(조명, 각도, 배경)" 성공률이라고 해서 표의 행 구분과 이름이 다르다.
- **"웹캠 보드 (선택)"**: 최종 결과물 3번 제목이 "웹캠 보드"인데, 내용상 "웹캠 모드"의 오타로 보인다. 이 README는 "웹캠 모드"로 적었다.
- **결과물 파일 이름과 보고서 형식**: 애플리케이션 파일 이름과 보고서 형식(Markdown, PDF, 노트북 등)을 명세가 정하지 않았다.
